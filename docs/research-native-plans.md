# Hooks converge while native plans quietly disappear

Every major coding-agent CLI now has a hook system close enough to Claude Code's (PreToolUse, PostToolUse, Stop, plus session events) that one verifier core with thin per-harness adapters can gate "done" everywhere. The native plans those hooks would check against are going the other way. They are fragmenting, they are mostly flat lists that get replaced wholesale with no step IDs, and they are increasingly **off by default**. Claude Code drops its Task tools on models newer than Opus 4.7 / Sonnet 4.6 / Haiku 4.5. Codex's `update_plan` reportedly became opt-in on 31 Aug 2026. Gemini CLI is moving from `write_todos` to an experimental tracker, and Antigravity's plan is free-form Markdown with no published schema. Only one harness has a true per-step veto: Claude Code's `TaskCompleted` hook. The web surfaces (claude.ai/Cowork, ChatGPT agent, the Gemini app) expose no plan at all, so there a verifier can only attest when called over MCP. It cannot enforce. The research says treat whatever plan the agent declares as a set of claims to check, not as ground truth. Only 22–45% of plan-then-act trajectories keep their declared structure, and agents report mid-task progress correctly as little as 5.8% of the time. A vendor-neutral verifier that imposes no methodology should therefore do three things. It reads native plan state when it exists and treats "no plan" as a normal state. It verifies status transitions against evidence the harness itself observed. It reports verdicts back as factual observations through each harness's own channel, and never rewrites the plan or dictates how the agent should plan.

## Native plans are flat, replace-whole lists, and more of them are opt-in

Compared side by side, the plan surfaces share a common core. Each is an ordered list of steps with roughly `pending | in_progress | completed` status. They differ in three ways that matter to a verifier: whether steps have stable identity, whether the list exists by default, and how faithfully the plan reaches an external observer.

| Surface | Native plan object | Step identity | Default state (Nov 2026) | Best read tap |
|---|---|---|---|---|
| Claude Code CLI / Agent SDK | `TaskCreate/Get/List/Update`; legacy `TodoWrite`; `ExitPlanMode` plan text | Task IDs returned in tool result; `blocks`/`blockedBy` edges | Off on newer models; on in cloud and background sessions | PostToolUse hooks; stream-json `tool_use` + `tool_use_result` |
| Codex CLI | `update_plan {explanation?, plan[{step, status}]}` | None (full replace) | Reportedly opt-in since 31 Aug 2026 | App-server `turn/plan/updated` |
| Gemini CLI | `write_todos`; experimental `tracker_*` | None / 6-char hex ID with dependency DAG | Tracker experimental | `AfterTool` hook |
| Antigravity (CLI, IDE, App) | Implementation Plan and Walkthrough Markdown artifacts; "task groups" UI | None (free Markdown) | Planning mode or `/plan` | PostToolUse on artifact writes; `artifactDirectoryPath` |
| Jules | `Plan {id, steps[{id, title, index}]}` | Step IDs | Plans auto-approved unless `requirePlanApproval` | REST polling of activities |
| ACP (any ACP agent) | `plan` session update, entries `{content, priority, status}` | None (full replace) | Protocol-level | ACP client or proxy |
| claude.ai / Cowork, ChatGPT agent, Gemini app | None exposed to integrators | — | — | MCP tool calls only |

Claude Code has the richest schema. `TaskUpdate` carries `taskId`, a status enum that includes `deleted`, `addBlocks`/`addBlockedBy`, `owner`, and a free-form `metadata` object. `TaskCreateOutput` returns the task's `id` ([Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)). Two details catch naive adapters. **The task ID is not in the `TaskCreate` input**: it arrives in the `tool_use_result` of the following user message, paired by `tool_use_id`. And the streamed input is "the raw shape the model emitted": Claude Code silently repairs `id`/`task_id` to `taskId` before execution, but the stream does not show the repair ([Agent SDK: Track todos](https://code.claude.com/docs/en/agent-sdk/todo-tracking)). The larger finding is about availability. Since v2.1.268, the task tools "are available by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5, and earlier models". On newer models, "Claude keeps track of multi-step work without a written checklist", and "Claude adds nothing to the task list while it works" unless the integrator opts in with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `--allowedTools TaskCreate`, or SDK `allowedTools`. Cloud and background sessions keep the tools on every model ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference#task-tool-availability)). Plan mode is a separate surface. `ExitPlanMode` returns `plan` and `filePath` in its PostToolUse `tool_response`, and the docs advise reading `tool_response.plan` rather than re-reading the file ([Hooks reference](https://code.claude.com/docs/en/hooks)).

Codex's `update_plan` is strict and minimal. The schema has `additionalProperties: false`, allows at most one step `in_progress`, and replaces the whole plan on every call ([codex plan_spec.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/plan_spec.rs)). Where you read it matters. The `codex exec --json` stream turns each plan into a `todo_list` item of `{text, completed: bool}`. That **collapses `pending` and `in_progress` into one value and drops `explanation`**, and the unified diff event is dropped entirely ([event_processor_with_jsonl_output.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/event_processor_with_jsonl_output.rs)). The app-server's `turn/plan/updated` notification keeps the full three-value status and the explanation, and `turn/diff/updated` carries the unified diff ([app-server v2/turn.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/turn.rs)). OpenAI now positions the app server as the integration surface for custom clients, and it has removed `codex mcp-server` ([Codex SDK docs](https://learn.chatgpt.com/codex/codex-sdk)). Post-hoc reconstruction has its own problem: the live `PlanUpdate` event is classed as transient and never written to the rollout. The plan survives on disk only as the model's `update_plan` function call ([rollout policy.rs](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/policy.rs)). The opt-in change comes from a single third-party post, which reports that PR #41744 made `update_plan` "disabled by default" behind `tools.update_plan.enabled` ([Daniel Vaughan blog](https://codex.danielvaughan.com/2026/08/31/codex-cli-update-plan-tool-opt-in-external-planning-competing-surfaces/)). The tool is still present in `main` source. Treat the opt-in default as likely but not independently confirmed.

Google's harnesses are the most fragmented. Gemini CLI's `write_todos` overwrites the full list of `{description, status}` items, with status values `pending`, `in_progress`, `completed`, `cancelled` and `blocked` ([write-todos.ts](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/packages/core/src/tools/write-todos.ts)). The experimental tracker adds typed tasks (`epic`/`task`/`bug`), hex IDs, parents and a dependency DAG, persisted per session under `.gemini/tmp/tracker/` ([Gemini CLI tracker](https://geminicli.com/docs/tools/tracker)). Gemini CLI also stopped serving Google AI Pro/Ultra and free individual users on **18 June 2026**. Its skills, hooks and extensions carried over to the Go-based Antigravity CLI ([Google Developers Blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)). Antigravity in turn has no typed todo tool. Its plan of record is the Implementation Plan artifact: rich Markdown with "task breakdowns and verification checkpoints", approved with **Proceed**, after which the agent "follows the approved plan step-by-step, validating each milestone with tests" ([Antigravity /plan docs](https://antigravity.google/docs/plan)). On completion it writes a Walkthrough artifact with "Validation Results" ([Antigravity walkthrough docs](https://antigravity.google/docs/walkthrough)). The official docs give no file path or schema. Hooks receive `artifactDirectoryPath`, and the `write_to_file` tool takes `IsArtifact` and `ArtifactMetadata` arguments ([Antigravity hooks](https://antigravity.google/docs/hooks.md)). The only published on-disk layout, `~/.gemini/antigravity/brain/<uuid>/task.md` as "the plan of record", comes from a community post ([Poehnelt](https://justin.poehnelt.com/posts/extracting-gold-from-antigravitys-brain/)). Jules is the exception among Google products. Its alpha REST API returns typed `Plan` objects with step IDs in `planGenerated` activities, has an `AWAITING_PLAN_APPROVAL` state, and offers `:approvePlan` and `:sendMessage`. It has no hooks or push notifications, and its `progressUpdated` activities are free text with no link to step IDs ([Jules API](https://developers.google.com/jules/api)).

ACP is the only interoperability standard that carries an agent's plan as a first-class object. Each `session/update` with `sessionUpdate: "plan"` must include "the complete list of entries", and "the Client replaces the whole checklist". Newer `planId`/`plan_update`/`plan_removed` variants appear on the same page, but their stability is unverified ([ACP Agent Plan](https://agentclientprotocol.com/protocol/agent-plan)). ACP has broad reach: the ACP Registry, live since 28 Jan 2026, lists Claude Code, Codex CLI, Copilot CLI, OpenCode and Gemini CLI ([Zed blog](https://zed.dev/blog/acp-registry)). That makes an ACP proxy the most harness-independent way to read plans on IDE surfaces. No such verifier proxy exists yet.

These shapes add up to one normalization target: `{id?, text, status, parent?, deps?, source}`, where the status superset is `pending | in_progress | completed | blocked | cancelled | deleted`. Only Claude's Task tools, Gemini's tracker and Jules supply native IDs. Everywhere else the verifier must derive step identity, for example from normalized text plus position across successive snapshots, and detect a "step boundary" as a status flip between two snapshots.

## Hooks share a vocabulary but differ exactly at the step boundary

The hook vocabulary is near-universal at the session level. At least six harnesses (Claude Code, Codex, Antigravity, Cursor, Copilot, Goose) can block a stop or force continuation, so a deterministic "done gate" is portable ([cross-harness survey: Cursor hooks](https://cursor.com/docs/agent/hooks); [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference); [goose hooks](https://goose-docs.ai/docs/guides/context-engineering/hooks/)). The harnesses diverge at the moment a verifier cares about most, when a plan step is marked complete.

| Harness | Step-boundary signal | Channel back to the model | Done gate |
|---|---|---|---|
| Claude Code | `TaskCreated` / `TaskCompleted` events; PostToolUse matcher `TaskUpdate\|TodoWrite\|ExitPlanMode` | `additionalContext` (system reminder); `updatedToolOutput`; exit-2 stderr as tool error | Stop `decision:"block"` + `reason` |
| Codex CLI | PostToolUse on `update_plan` (inferred, untested); app-server `turn/plan/updated` | `additionalContext`; PostToolUse block replaces result with feedback; `turn/steer` | Stop `decision:"block"` forces continuation |
| Gemini CLI | `AfterTool` on todo tool | `additionalContext` appended to tool result | `AfterAgent` deny / exit 2 forces retry |
| Antigravity | PostToolUse on artifact writes (can return only `{}`) | `injectSteps` at Pre/PostInvocation | Stop `decision:"continue"` + `reason` |
| Cursor / Copilot | postToolUse | `additional_context` / `additionalContext` | stop `followup_message` / agentStop block |
| Kiro | Pre/Post Task Execution (payload undocumented) | `agent` action; Post Tool Use | Subagent Stop only |

Claude Code's `TaskCompleted` is the only native per-step veto. On exit code 2, "the task is not marked as completed and the stderr message is fed back to the model as feedback". The official example runs `npm test` and blocks with "Tests not passing. Fix failing tests before completing". When `TaskUpdate` triggers the event, `continue: false` is ignored but exit 2 still blocks. `TaskCreated` can also roll back a task's creation ([Hooks reference: TaskCompleted](https://code.claude.com/docs/en/hooks#taskcompleted)). The Stop hook adds a final gate. `decision:"block"` with a required `reason` keeps Claude working, `stop_hook_active` and an 8-consecutive-continuation cap prevent loops, and `last_assistant_message` is the reliable read because "the transcript file isn't guaranteed to include the final message at Stop time" ([Hooks reference: Stop](https://code.claude.com/docs/en/hooks#stop)). Three caveats limit this surface. `TaskCompleted` exists only when the Task tools exist. TodoWrite sessions can be policed only by diffing `oldTodos`/`newTodos` after the fact, or by denying the TodoWrite call in PreToolUse. The **Python Agent SDK does not support `TaskCreated` or `TaskCompleted` callbacks** ([Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)). And async hooks "can't block or control Claude's behavior" ([Hooks reference](https://code.claude.com/docs/en/hooks)).

Codex adopted Claude-compatible I/O: `hookSpecificOutput.additionalContext`, `permissionDecision`, `decision:"block"` and exit code 2. Hooks are on by default across 14 events. A PostToolUse block "Replaces the result with feedback. Does not undo the tool's side effects". `prompt` and `agent` handlers "are parsed but skipped", and non-managed hooks must pass a trust review tied to their hash ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). Nothing in the docs confirms that `update_plan` reaches the tool hooks. It is a plain function tool in source ([plan.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/plan.rs)), so a matcher should fire, but that needs an empirical test. Gemini CLI offers the cleanest typed loop among Google tools. An `AfterTool` hook sees the full todo list, and its `additionalContext` is appended directly to the tool result the model reads ([Gemini CLI hooks reference](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/hooks/reference.md)). Antigravity's six hooks control behavior through stdout JSON rather than exit codes. Its PostToolUse returns only `{}`, so feedback after a plan edit has to wait for a `PostInvocation` `injectSteps` system message or a Stop `decision:"continue"` ([Antigravity hooks](https://antigravity.google/docs/hooks.md)). In headless `agy -p`, unobtainable approvals are **soft-denied and the run still exits 0** ([Antigravity headless](https://antigravity.google/docs/cli/headless)). Exit code alone therefore says nothing about whether the requested work ran.

Portability is real but informal. Cursor loads Claude Code hooks, matches its exit-2 semantics and aliases `CLAUDE_PROJECT_DIR` ([Cursor hooks](https://cursor.com/docs/agent/hooks)). Copilot reads `.claude/settings.json` from the repository ([Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference)). A Claude-format hook pack therefore covers three harnesses. Decision vocabularies still differ (`block`, `continue`, `followup_message`, `force_continue`), and one practitioner audit found Codex and Claude Code hooks "not as portable as they look" because of handler types, matchers and config locations ([dev.to audit](https://dev.to/nekoautomata/your-codex-and-claude-code-hooks-are-not-as-portable-as-they-look-5340)). The adapter should emit one normalized verdict and render it per harness.

Observation channels need the same care. Claude Code transcripts live at `~/.claude/projects/<project>/<session-id>.jsonl`, but "the entry format is internal to Claude Code and changes between versions", and the docs point integrators to hooks, `-p --output-format stream-json`, or the SDK ([Manage sessions](https://code.claude.com/docs/en/sessions)). `--bare`, which "will become the default for `-p` in a future release", skips hook and plugin auto-discovery. A verifier shipped as a plugin will then load in scripted runs only when passed explicitly, and `system/init`'s `plugins` field lets CI check that it loaded ([Headless](https://code.claude.com/docs/en/headless)).

## Web and cloud surfaces allow attestation, not enforcement

The consumer web surfaces close off native plan state entirely. The notes found no documented API, hook or export for a to-do or plan inside claude.ai chat or Cowork. Cowork scheduled tasks share connectors, skills and plugins but describe no progress list ([Cowork scheduled tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)). ChatGPT agent offers users "on-screen narration" and the ability to "pause it, ask it for a progress summary, or stop it", with no integrator-facing plan object ([Introducing ChatGPT agent](https://openai.com/index/introducing-chatgpt-agent/)). Gemini's Deep Research plan is editable in the UI only ([Gemini Help](https://support.google.com/gemini/answer/15719111)). The supported way in is a remote MCP server. claude.ai has "Full remote MCP support & MCP Apps" ([Claude connectors overview](https://claude.com/docs/connectors/overview)). ChatGPT developer mode supports read and write tools, and write actions "require confirmation by default" unless the tool declares `readOnlyHint` ([OpenAI developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). Google's Connected Apps MCP path sits behind an interest form ([Google Connected Apps](https://developers.google.com/connected-apps/mcp)). On these surfaces a verifier is something the model calls voluntarily, and its verdicts carry weight only if it re-runs checks in its own runtime and a downstream gate (CI, the PR, a ledger) enforces them.

Cloud coding agents sit between the two tiers. Claude Code cloud scheduled tasks run "as full Claude Code cloud sessions" that load skills committed to the repo ([Routines](https://code.claude.com/docs/en/routines)), and cloud sessions keep the Task tools on every model. Repo-committed hooks are likely to run there too, though the fetched text does not explicitly confirm it. The routine docs carry a warning worth remembering: run status "say[s] how the session ended, not whether Claude completed the work your prompt describes" ([Routines](https://code.claude.com/docs/en/routines)). Codex cloud lists no results API or webhook. Its hooks page says only that "Cloud orchestration supports only Global MCP hooks" ([Codex hooks](https://learn.chatgpt.com/docs/hooks)), which leaves the environment install script and post-hoc CI checks on the diff as the practical insertion points ([Codex cloud](https://learn.chatgpt.com/docs/cloud)). For long verification runs, MCP's experimental tasks (`working`, `input_required`, `completed`, `failed`, `cancelled`, with `isError` mapping to `failed`) fit a "re-run the suite" call ([MCP Tasks spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)). Whether each harness implements tasks on the client side is unverified. None of ACP, MCP tasks, A2A TaskState or the OTel GenAI agent spans defines a record of the form "step claimed done, evidence, verifier, verdict". That schema slot is open ([MCP changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog); [A2A spec](https://a2a-protocol.org/latest/specification/)).

## Research treats declared plans as claims and favors observed evidence

The empirical case for step-level verification rests mostly on 2026 preprints, which are unreviewed but consistent with one another. In "Do LLM Agents Execute the Plans They Declare?", **only 22–45% of Plan+ReAct trajectories preserved their declared structure**, with SWE-bench Verified rates of 12–25%. On ALFWorld, structure maintenance fell from 36.5–49.6% for 4–5-step plans to **0% for plans longer than seven steps**. Hierarchical plans fully completed only 30–41% of the time ([arXiv 2609.38108](https://arxiv.org/html/2609.38108v1)). Self-reported status is weaker still. "The Unreliable Progress Bar" found gpt-4.1 and gpt-5.5 reporting the correct lifecycle stage at 90.6–99.4% of pre-action checkpoints but **only 5.8–11.5% mid-task**. Newer models shifted the weakness to completion (48–64%). False completion rose from 6.2% to 64.4% when a tool was withdrawn. Reminders and gold-injected stage hints did "not generally close the gap", and the authors conclude frameworks "should not control task flow on the strength of the model's state reports alone" ([arXiv 2609.08589](https://arxiv.org/pdf/2609.08589)). Put together, these findings mean a native todo flipped to "completed" is exactly the signal that cannot be trusted on its own. It is also exactly the signal hooks like `TaskCompleted` let a verifier intercept.

Two findings shape *what* to verify. First, humans barely agree on whether a plan was followed in order: κ = 0.35 between annotators, with a rule-based structure checker at κ = 0.31–0.34 ([arXiv 2609.38108](https://arxiv.org/html/2609.38108v1)). That argues for checking **per-step postconditions** (did evidence for step k appear?) and allowing interleaved extra work, rather than enforcing strict order. A verifier built this way also avoids imposing a methodology, since it never tells the agent how to sequence its work. Second, the evidence must not be under the agent's control. Qwen's "Verification Horizon" measured a 37.76% hack rate on SWE-bench variants before mitigation, including **evaluation-harness tampering in 8.25% of trajectories**. It calls unit tests "scalable and robust but shallow" and LLM judges "scalable and faithful but exploitable" ([arXiv 2606.26300](https://arxiv.org/pdf/2606.26300)). A practitioner "verify-before-stop" hook showed the same failure in small: a bogus VERIFIED line written by the agent passes the check ([dev.to/ianymu](https://dev.to/ianymu/how-3-claude-code-hook-strategies-compare-for-preventing-false-completion-d7m)). A step "verified by tests" whose own diff touched those tests or their config should be treated as suspect. That rule is cheap and deterministic.

Cheap deterministic signals at the step boundary pay off. In SWE-agent, linting on edits was worth 18.0% vs 15.0% resolved on SWE-bench Lite. A single failed edit dropped the chance of eventual success from 90.5% to 57.2%. Keeping only the last five observations beat full history, which favors compact diagnostics over verbose logs ([SWE-agent, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)). Deterministic AST checks for hallucinated Python APIs reached 100% precision and 87.6% recall in under 0.2 seconds for 200 samples, though only across five libraries ([FORGE '26, arXiv 2601.19106](https://arxiv.org/html/2601.19106v1)). Step-level supervision beating outcome-only supervision has older support from PRM work on MATH ([Let's Verify Step by Step](https://arxiv.org/abs/2305.20050)). LLM judges add coverage: the factorized "Agent GPA" judges caught 95.0% of human-labeled errors vs 54.8% for a monolithic judge ([arXiv 2510.08847](https://arxiv.org/pdf/2510.08847)). Given the exploitability findings, they belong in an advisory tier above deterministic gates.

Runtime verification answers *how* to intervene. AgentLTL checks each proposed tool call against the trace prefix before execution. **Block-and-warn improved compliance on 5 of 7 models, while soft-block (terminate after three violations) was the worst setting for 4 of 7**. Ordering constraints accounted for most violations ([arXiv 2607.02599](https://arxiv.org/html/2607.02599v1)). ContrAgent compiles assume-guarantee contracts to a DFA used both online and offline, and reports latency "orders-of-magnitude lower" than LLM-judge guardrails ([arXiv 2609.18128](https://arxiv.org/html/2609.18128)). PIVOT's repair loop localizes the *earliest* failed step and rewrites only the unsupported suffix. With human feedback it lifted shopping-case accuracy from 10.8 to 76.7 on Qwen3-235B ([arXiv 2605.11225](https://arxiv.org/html/2605.11225v1)). The WHO surgical checklist supports checking at a few phase boundaries rather than constantly: three checkpoints cut major complications from 11% to 7% across 7,688 patients ([Harvard Gazette](https://news.harvard.edu/gazette/story/2009/01/surgical-safety-checklist-drops-deaths-and-complications-by-more-than-one-third/)). The research leaves one question open: whether verifier feedback works better in a tool result, a system reminder or a user turn. No controlled study exists. Instruction-hierarchy training gives lower-privilege text less weight as an instruction ([arXiv 2404.13208](https://arxiv.org/abs/2404.13208)), so phrasing verdicts as *observations about state* rather than commands is a reasonable design choice, though it has not been measured.

## A methodology-neutral contract has five rules

Putting the surfaces and the science together gives an integration contract that works with each harness's native features instead of replacing them. **First, ingest read-only and accept absence.** The verifier subscribes to whatever plan the harness already emits: Claude Task/TodoWrite/ExitPlanMode via PostToolUse, Codex `turn/plan/updated`, Gemini `AfterTool`, Antigravity artifact writes, Jules activities, ACP `plan` updates. It treats "no plan" as a first-class state rather than a failure. Turning on `CLAUDE_CODE_ENABLE_TODO_TOOLS` or `tools.update_plan.enabled` is itself a methodology choice, and Anthropic says the tools' "definitions and reminders take up context" ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference#task-tool-availability)). Opt-in should stay a user setting, not something the verifier forces. Without a native plan, the verifier falls back to the plan the user or a handoff brief supplied, or to session-level gates only. **Second, normalize to the superset schema and derive identity** where the harness gives none. **Third, verify at transitions, not continuously**: `in_progress→completed` flips, `TaskCompleted`, and Stop. That matches the checklist evidence and keeps overhead low. **Fourth, gate only on harness-observed evidence**: process exit codes, real diffs (Codex `turn/diff/updated`, git), the verifier's own re-run of tests and type checks, and AST predicates. The tamper rule applies throughout. Agent-written attestations count for nothing. LSP diagnostics belong in the secondary tier, because Claude Code leaves its LSP tool inactive in cloud sessions ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference#lsp-tool-behavior)) and OpenCode ships with LSP disabled by default ([OpenCode LSP](https://opencode.ai/docs/lsp/)). **Fifth, render one verdict per harness as block-and-warn observations** ("step 3 marked done; no diff touches `auth/`; 2 new type errors in `session.ts`"). Feedback should name the earliest unverified step and never terminate the session.

This contract also marks out the gap among existing tools. Ralph Loop, with 196,527 installs, re-feeds the prompt "until Claude outputs the completion promise", which is a done signal the agent controls ([Ralph Loop plugin](https://claude.com/plugins/ralph-loop)). Probity enforces process rules per action across four harnesses from one config ([Probity](https://awesome.ecosyste.ms/projects/github.com%2Fnizos%2Fprobity)). TDD Guard prescribes TDD outright ([TDD Guard](https://github.com/nizos/tdd-guard)), which is precisely the methodology imposition the question rules out. None of the tools surveyed binds verification to individual native plan entries. The negative search result is suggestive rather than conclusive.

## Conclusion

The striking shift is that vendors are withdrawing the very checklist a verifier would read, on the theory that frontier models track multi-step work internally. At the same time the best evidence shows that internal tracking is exactly what fails mid-task and at completion. So the durable design treats the harness's plan as an optional, lossy hint and treats harness-observed evidence as the ground truth. The Stop gate is the reliable common denominator, and `TaskCompleted` is a bonus that is currently Claude-only. The one place the verifier can be genuinely novel is the plan-versus-trace comparison itself. Formal process-mining alignments would sort every event into evidenced steps, steps claimed without evidence, and unplanned work. The only paper found applying process mining to agent logs reports no fitness or alignment metric ([arXiv 2606.20669](https://arxiv.org/html/2606.20669v1)), and no benchmark reports evidenced-completion rates for commercial harnesses' native todo tools.

Two experiments would close the biggest unknowns cheaply. One is an empirical check that `update_plan` and Antigravity artifact writes actually reach PreToolUse/PostToolUse matchers. The other is an A/B test of verdict placement (tool result vs. system reminder vs. Stop reason) on a regression suite. The first decides whether per-step gating is possible outside Claude Code. The second decides how to phrase every verdict the verifier emits, and the research has nothing on it yet.
